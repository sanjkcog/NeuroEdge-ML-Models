# `mcp/` — the tool-server face

Two files, and they have **different owners**. That is the whole reason this is a directory rather
than one file.

| File | Owner | What it says |
|---|---|---|
| `servers.json` | **generated** — do not edit | which tool servers exist, and what each one offers |
| `responses.json` | **authored** — never generated | what each tool answers |

## `servers.json` is derived, and the face refuses it if it is not

A tool server is not asked for an address; it is asked *what tools do you have*, and the client
calls one of the answers. So a hand-written tool list can advertise a tool production does not have,
or describe one with the wrong arguments — and a rehearsal against it passes right up until the real
call fails. The list is therefore generated by the host from what it discovered from the real
servers, and the file must say so:

```json
{
  "source": "discovery-cache",
  "generated_by": "<the host's discovery tool>",
  "servers": [
    {
      "id": "example_server",
      "address": "https://example.invalid/mcp",
      "description": "What this stands in for, in one line.",
      "tools": [
        {
          "tool_name": "lookup_thing",
          "description": "What the real tool does.",
          "input_schema": {"type": "object", "properties": {"id": {"type": "string"}}}
        }
      ]
    }
  ]
}
```

A file whose `source` is anything else is **refused**, by name, with the reason. `address` is the
*real* server's address: it is carried so a reader can see which production system this stub stands
in for, and so the overlay has something to replace. Nothing in the simulator ever dials it.

## `responses.json` is an ordinary fixture file

Same shape as `fixtures/`, one extra key naming the server. `returns` xor `sequence`, optional
`caller` scoping, optional `faults` — nothing new to learn:

```json
{
  "responses": [
    {
      "server_id": "example_server",
      "tool_name": "lookup_thing",
      "returns": {"id": "abc", "status": "ok"}
    },
    {
      "server_id": "example_server",
      "tool_name": "lookup_thing",
      "caller": "second_hub",
      "sequence": [{"status": "ok"}, {"status": "busy"}]
    }
  ]
}
```

A tool the server advertises but nobody has authored an answer for fails **loudly** on call, naming
which key missed and which tools do have one. A tool nobody advertises cannot be called at all —
that answer is the real server's, and it is the point of generating the list.

## Pointing a capability here

The run writes each simulated server's address into `run/ports.<scope>.json` under `tool_servers`.
Put that address in `scenario.yaml`'s `env:` overlay for the variable the capability's binding
reads. Going real means putting the production address back in the same field.
