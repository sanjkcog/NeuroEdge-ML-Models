## What it does

1. Checks the folder: the lock is the one this code was generated for, and every file of the base model snapshot
   has the sha256 `/model-fetch` recorded.
2. **Uses no network.** `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` are set, and the model is loaded with
   `local_files_only=True` from `model/base/weights/`.
3. Reads `data/splits/train.json` and `val.json` only. Each unit lists its image files and its label.
4. Trains the **baseline** first: a linear probe (frozen backbone, new head). Then fine-tunes the whole network.
   Same split, same metrics. `model_artifact.json` records both and `beats_baseline`, **measured on validation**
   and labelled `measured_on: self_reported_val`. Validation also picked both best epochs, so that comparison is
   not a clean one. The baseline is therefore exported too (`model-package/baseline/model.onnx`), and `eval.py`
   scores **both** on the held-out split and writes `baseline` and `beats_baseline` into its metrics. M10 trusts
   that comparison. The baseline file doubles the size of the run folder; it is not part of the upload zip.
5. Picks the best epoch by validation macro-F1.
6. Exports ONNX through `optimum`, folds the normalisation (`Sub`, `Div`) into the graph, so the input is an image in
   `[0, 1]`, and checks the file with `onnxruntime`.
7. Writes `runs/<run_id>/model-package/`: `model.onnx`, `meta.json` (`output_schema: class_logits`),
   `model_artifact.json`, `metrics.json` (`eval_split: self_reported_val`).

## Two things this does not do for you

- **Near-duplicate images are not checked here.** The package builder refuses an image file that is listed on both
  sides of the split, and nothing more. Burst frames, re-encodes and crops of one capture are different files, and
  they leak just the same. That control belongs to the dataset verify stage (M4): split by source image and capture
  session, and look for near-duplicates there.
- **MLflow can send metrics off this machine.** `train.py` logs to MLflow when it is installed. With no
  `MLFLOW_TRACKING_URI` it writes to a local `./mlruns`. **If you set `MLFLOW_TRACKING_URI` to a remote server, the
  parameters, the per-epoch metrics, the use-case id and the lock hash are sent there.** Set it only to a server
  you mean to send them to.

## Steps

```
# 1. a machine with an NVIDIA GPU, Python 3.11
python -m venv .venv && . .venv/bin/activate
pip install --only-binary=:all: -r requirements.txt

# 2. from this folder
python train.py --config config.yaml

# 3. the result
ls runs/*/model-package/
```

The base model snapshot and the images must be in the model folder, at the paths the split files name. They are not
in git. A base model that needs a key was already fetched by `/model-fetch`; **no key is needed here.**

## Held-out evaluation

Only `/agentforge-ml` M10, or the portal's Evaluate step, runs this. It is the only code given `test.json`:

```
python eval.py --package runs/<run_id>/model-package --split ../data/splits/test.json --config config.yaml --out metrics_test.json
```

## As a training package

`python -m agentforge.src.ml_contract.package build --dest <model folder> --arch {{ARCH}}` zips this folder, the
lock, `model/base/` and the images the train and val units list. Every image a test unit lists is withheld and
sealed into `data/portal_test.zip`. **Unverified:** the portal's package runner has not run a vision package yet.
Until it has, run the steps above yourself; the result enters the portal as a return package.
